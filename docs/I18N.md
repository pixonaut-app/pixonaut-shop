# Internationalisation

English is the source language for every string in the theme; Swedish is the
shipped translation, in `languages/sv_SE.po` (and the compiled `sv_SE.mo`).
The text domain is `pixonaut-shop` — style.css's `Text Domain` and
`Pixonaut\Shop\I18n\TextDomain::DOMAIN` — and it never varies.

## What is translated, and what is not

The theme's **interface strings** are translated: the 404 page, the footer's
copyright line, the admin notice, the names of the colour, font and spacing
presets, the template parts and the style variations (WordPress reads those
from `theme.json` and `styles/*.json` through the same text domain).

A store's **content** is not: its pages, products, menus, site title and
tagline are written in the store's own language by its owner, and live in its
database. That is also why the templates hold no copy of their own.

WooCommerce's blocks — the cart, the checkout, the price, the add-to-cart
button — carry WooCommerce's own strings, translated by WooCommerce's
language pack, not by this theme.

## Where strings live

- **`inc/`** — `__()`, `esc_html__()` and friends with `'pixonaut-shop'`.
- **`patterns/*.php`** — the same, inline:
  `<?php echo esc_html__( 'Page not found', 'pixonaut-shop' ); ?>`. This is
  why the footer part is a reference to a pattern: an
  `.html` template or part cannot translate a string.
- **`templates/*.html` and `parts/*.html`** — no strings. A block attribute
  in an `.html` file (a prefix, a label) cannot be translated, so the
  templates use none; text a template needs goes into a pattern.

PHPCS fails on a translation call with any other text domain.

## The scripts

| Command | What it does | Run it when |
| --- | --- | --- |
| `pnpm i18n:pot` | Builds the theme, then regenerates `languages/pixonaut-shop.pot` from `inc/`, `patterns/`, `build/blocks/`, style.css, `theme.json` and `styles/`, with `wp i18n make-pot` in a `wordpress:cli` container (no wp-env needed). | Any translatable string is added, changed or removed. |
| `pnpm i18n:update` | Merges the POT into `languages/sv_SE.po`, keeping existing translations and marking new or changed ones untranslated or fuzzy. | After `i18n:pot`, before translating. |
| `pnpm i18n:mo` | Compiles `sv_SE.po` into `sv_SE.mo`, which WordPress reads, and the editor scripts' strings into their JSON catalogues. | After translating. |
| `pnpm i18n` | All three in order. | The normal case. |

Translate in `sv_SE.po` after `pnpm i18n:pot && pnpm i18n:update`, then run
`pnpm i18n:mo`, and commit the POT, the PO and the MO together, in the change
that added the string. `SwedishCatalogueTest` fails while any string is
untranslated or fuzzy.

## CI fails on a stale POT

The integration job regenerates the POT and `pnpm i18n:check` compares it
with the committed one by its strings alone: `#: file:line` references, the
`POT-Creation-Date` header and the order of entries change without any string
changing, so `scripts/ci/pot.ts` leaves them out. A failure prints each entry
found on one side only.

The editor script `src/editor/menu-heading.js` shows the store's own menu
names and has no strings of its own, so it needs no JSON catalogue.

## The blocks' editor strings

The blocks' editor scripts translate through JSON catalogues,
`languages/pixonaut-shop-sv_SE-<md5>.json`, one per built script, named by
the hash of its path (`build/blocks/<name>/index.js`) as WordPress looks it
up. `wp i18n make-pot` cannot read TypeScript, so `pnpm i18n:pot` builds
the theme first and reads the blocks' strings from `build/blocks/`, not
`src/`; the POT's references to them name the built files, which is what
`pnpm i18n:mo`'s `wp i18n make-json --no-purge` turns into those
catalogues. Commit the JSON files with the PO and MO. A block's title,
description and keywords come from its `block.json`, translated on the
server from the MO.
